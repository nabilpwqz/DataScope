# ADR-0001: RTK Query vs. Redux Async Thunks for Data Fetching

- **Status**: ACCEPTED
- **Author**: DataScope Architecture Working Group
- **Scope**: Enterprise Discovery Core Engine

---

## 1. Context & Problem Statement

Large enterprise datasets require automatic request deduplication, cache invalidation, serialized parameter caching, and background revalidation without maintaining thousands of lines of boilerplate reducers.

---

## 2. Considered Alternatives

1. Redux Async Thunks (requires manual lifecycle state tracking, manual cache structures, and boilerplate)
2. TanStack React Query + standalone Redux (introduces two conflicting state paradigms)
3. Native fetch inside useEffect (vulnerable to race conditions, memory leaks, and duplicate network requests)

---

## 3. Decision Outcome

**Selected Approach**: RTK Query with normalized tag-based invalidation (providesTags / invalidatesTags) and automatic 60-second unused data retention.

**Rationale**:
RTK Query integrates natively with Redux Toolkit store, provides automatic request deduplication for identical concurrent queries, automatically handles background polling and optimistic mutations, and provides type-safe autogenerated React hooks.

### Positive Consequences & Advantages:
- Zero manual action/reducer boilerplate for loading, error, and data states
- Automatic request deduplication prevents duplicate network flights for identical queries
- Granular cache invalidation via tag types (Dataset, Record, SavedView, Analytics)
- Integrated seamlessly with the required Redux Toolkit store

### Negative Consequences & Trade-offs:
- Slight learning curve for tag invalidation semantics
- Requires standard serializable query arguments

---

## 4. Performance Implications

Eliminates over 80% of redundant network flights through in-flight deduplication and memory cache reuse.

---

## 5. Future Scalability & Limitations

For complex offline-first write mutations, persistent indexedDB storage adaptors would be required.
